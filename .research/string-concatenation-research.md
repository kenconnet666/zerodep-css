# JavaScript 字符串拼接研究

日期：2026-09-26。范围：现有运行时 `css(...parts: string[])` 注册器；保持直接字段作者模型，不引入编译器、不更改产品实现。

后续已经完成两轮 Vue/Svelte 真实组件验证与静态前缀探针：暂保留产品的 `join`，转向框架使用体验，详见[组件复测与下一阶段](framework-performance-next-stage.md)。下文是候选形成时的微基准记录。

## 结论

没有找到值得为当前路径引入的字符串构建库。原生 `+=` 循环值得作为下一步小改动候选，但收益集中在重复调用注册器；不能把这项结果换算成整个组件或页面的提速。

目前注册器先拼接，再以完整正文查 `Map`，命中则直接返回类名。已有规则避免了重新生成规则，但仍然需要得到缓存键。候选优化只改变这一步，保持输入顺序、空字符串、原生层叠与哈希命名不变。

## 引擎与库的实际做法

| 方向                      | 实际实现                                                                       | 对本项目的价值                                            |
| ------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------- |
| 原生 `+` / `+=`           | V8 的 `StringAdd` 在部分路径使用引用左右子串的 `ConsString`，其他路径直接复制  | 值得测，但不能只读取 `.length` 就宣称省掉了所有复制成本   |
| 原生 `join('')`           | V8 汇总片段及长度，再生成连续字符串；另有空结果、单片段快捷路径                | 已有引擎优化，不是天真的反复完整复制                      |
| `halil/string-builder`    | 数组收集片段，`toString()` 调用 `join('')`；当前 CommonJS 实现继承 Node Stream | 对当前已有 `parts` 数组的浏览器路径没有新算法优势         |
| `tsdotnet/string-builder` | 数组加 `join('')`，并缓存最近一次 `toString()` 结果，追加内容时失效            | 可借鉴“输入不变就复用结果”，不必引入可变构建器            |
| `clsx/lite`               | 循环 `+=`，附带过滤与空格分隔                                                  | 值得参考短循环；它处理类名列表，不能直接替换 CSS 正文拼接 |

V8 来源是研究当天的主分支，解释可能的实现机制，不证明 Chrome 153 的每条优化路径完全一致。不能从源码推导 `+` 在所有字符串长度、字符集和浏览器中都更快。

一手来源：

- [V8 StringAdd](https://github.com/v8/v8/blob/main/src/builtins/builtins-string-gen.cc)
- [V8 Array.join / BufferJoin](https://github.com/v8/v8/blob/main/src/builtins/array-join.tq)
- [string-builder 实现](https://github.com/halil/string-builder/blob/main/src/stringbuilder.js)
- [tsdotnet StringBuilder 实现](https://github.com/tsdotnet/string-builder/blob/master/src/StringBuilder.ts)

## 当前注册器探针

运行：`pnpm --dir .research/string-css-probe probe:string-concat`。

探针读取实际 `core/src/registry.ts`，在内存中仅替换 `const body = parts.join('')`，通过 esbuild 生成相同目标的代码。对比六种方法：原始 `join`、索引循环 `+=`、`concat(...parts)`、`reduce`，以及 1—2 / 1—4 参数使用直接加法、其余使用 `join` 的版本。

环境为 Windows、Node 24.18.0、Chrome 153.0.8010.54。每组 7 轮、轮换执行顺序；每个变体先预热 20,000 次，再测 100,000 次命中。16 组预制输入循环使用，保留参数展开、rest 参数、拼接和实际 `Map` 查找。新规则另测 1,400 次，计入原有哈希、Map 登记与 CSSOM `insertRule`，不计输入生成和样式表创建，不强制布局。

覆盖 1、2、4、8、32 片段；ASCII 组使用自定义属性与宽度，Unicode 组在前面的片段加入中文和 emoji。单片段时两组都是宽度，只是两次不同运行时机的对照。验证空参数、空片段、输出类名、正文顺序、规则数量，浏览器与临时样式表均由 `finally` 清理。

原始记录保留于 [首轮](string-css-probe/results/string-concat.json) 和 [复测](string-css-probe/results/string-concat-repeat.json)。这不是独立库之间的实测；库的判断来自源码。两次本机 Chrome 测量也不构成跨浏览器结论或 CI 性能门槛。

两次各自的 7 轮中位数范围，单位毫秒，越低越好：

按每次运行内部对应中位数比较，`+=` 在全部 2—32 片段的命中样本中耗时降低约 12%—21%，单片段降低约 54%—57%。但不同运行时机有明显波动，尤其第二次 ASCII 32 片段；这些百分比不是稳定性能承诺。`reduce` 与循环接近，部分样本更快；`concat` 和少量参数特化也没有统一胜出，因此不值得为了这轮排名添加多档选择逻辑。

新规则包含 CSSOM 后，没有稳定的整体收益；ASCII 32 片段复测反而从 38.5 ms 增至 44.9 ms。即使典型 8 片段命中路径降低约 15%，绝对节省也只是每 100,000 次约 7 ms，不能外推为页面快 15%。未测 Firefox/WebKit、堆内存或 GC 分配量；本轮也未覆盖巨大参数列表、动态创建片段的额外成本与组件渲染。

## 建议的落地顺序

1. 下一轮如修改注册器，优先验证简单 `+=` 循环；它比引入构建器或多档参数分支更容易维护。产品路径依旧只接受声明字符串，不为任意类型转换扩大 API。
2. 先使用现有能力复用完整静态类名；必须与动态声明组成同一规则时，再把相邻静态片段提前拼成一个字符串，保持原有顺序。前者能避免重复调用整个注册器，后者只减少每次处理的片段数。
3. Vue/Svelte 中利用 `computed` / `$derived` 管理适合的派生结果，有限分支直接选已注册类名，减少调用次数。具体生命周期与副作用边界沿用[框架结合研究](vue-svelte-runtime-integration.md)。
4. 不为短 CSS 声明新增 Node Buffer、WASM 内存或自建 rope；它们最终仍需交回 JS 字符串供 Map / CSSOM 消费。若未来出现大体积 SSR 文本流，再围绕那个独立场景测试。

本轮只增加研究脚本和记录。产品运行时仍使用 `join('')`；没有新增依赖，没有改变公开写法。
