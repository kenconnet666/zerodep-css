# 下一阶段：补齐类型交付并整理生成代码

本轮先规划，不改动试验 API。当前脚本已从固定的 `csstype@3.2.3` 生成 **502 条标准与独有 SVG 属性链、12,586 个可命名关键字**。`raw()` 允许任意字符串并提供已知值提示；接受长度的属性才有 `px()`；Vue/Svelte 可通过 `class AppCss extends Css` 和 `createCssContext<AppCss>()` 保留主题类型。这达到了此前约定的**属性生成范围**，但尚未达到“外部项目拿来就有完整可靠类型”的交付标准。

## 建议的实施顺序

1. **声明与条件导出。** 把相对 TS 导入写成可同时被 Bundler 与 NodeNext 解析的 `.js` 路径；让包类型入口指向构建出的 `.d.ts`。针对 `browser`、`node` 与显式 `/server` 入口设计成对的 JS/类型条件，特别核对 Vue/Svelte 根入口在 Node SSR 下的导出集合。增加一个只通过包名导入的消费者夹具，不依赖源码路径。此步单独提交，避免目录调整掩盖类型回归。
2. **生成器与类型覆盖。** 保持一个清楚的数据来源和一条生成命令。先补生成正确性的断言与关键类型例子，再按固定字母区间将 502 条链分成约 6–8 个文件，另设一个生成入口汇总 `Css` 与导出；手写的主题类继续继承公开的属性链类。拆分不改变 `s.color.red`、`s.width.px(24)`、`s.width.raw('...')` 的结果，也不额外生成页面 CSS 规则。若测得 LSP 或冷导入明显退化，保留单文件并只改善脚本和导航文档。单独提交。
3. **命名与目录。** 规则注册器内部改名，保持公开的 `css()`、`ic()`、`Css`、`createCssContext()`、`provideCss()`、`useCss()` 和 `CssRule` 不变。把旧探针、现行 Vue/Svelte 夹具、基准入口、原始结果分目录；同时修正脚本相对路径、文档链接和过时状态描述。不引入第二套同义 API，也不删除有研究价值的原始样本。单独提交。

## 类型范围与不做的事

“完整”在本阶段指**既定 502 属性范围内的可用、可继承、可从正式包入口消费的类型**，不是浏览器 CSS 语法的静态验证器。厂商前缀、过时属性和 `--custom-property` 尚无专用链；用户可继续向 `css()` 传原生声明字符串。`raw()` 保持开放字符串，浏览器决定值的有效性。`ic()` 保持常见选择器补全与任意字符串，不逐条编码所有伪类、媒体查询或 CSS 语法。未来的响应式 CSS 变量绑定编译属于独立阶段，不借这轮类型整理改写运行时语义。

每步验收以 `pnpm check`、`pnpm build`、外部 Bundler/NodeNext 类型夹具和现有 Vue/Svelte 浏览器、Node SSR、hydration 测试为主。生成模块拆分与导出调整再对照当前冷导入和 LSP 补全基线；只有运行时代码确实改变时才重跑完整性能比较。Nuxt/SvelteKit 仍是预留包，不将空入口误报为类型完善。

## 实施记录

- 类型入口已改用 `dist/types`，Vue/Svelte 的 Node 条件使用服务端声明。临时外部消费目录中的 Bundler 与 NodeNext 类型夹具均通过；临时目录由检查脚本在结束时移除。
- 生成结果按稳定名称区间分成八个属性文件，加一个共享基类文件与汇总入口。`--check` 仍逐文件核对确定性输出，属性与关键字数量保持 502／12,586。
- 同机单次测量：生成检查从约 7.54 秒到 7.21 秒；core 类型检查从约 6.03 秒到 6.16 秒。微小差异不足以判定性能变化。`core/dist/index.js` 拆分前后均为 590,172 字节；LSP 在拆分后仍能补出 `s.width.px`。Vue/Svelte 的浏览器、Node SSR 和 hydration 产物测试通过。
