# 直接字段版的优化研究

后续方向已改为先研究[运行时同步快路径、并行与 SIMD](runtime-parallel-simd-research.md)；下文的静态类名提取仍是可选候选，不是必做的编译器路线。

本轮只研究候选实现与静态分析，未改产品运行时代码。基线是[直接字段试验](direct-keyword-fields-probe.md)：固定声明为 `readonly red = 'color:red;'`；`css(...parts)` 已对完整字符串组合缓存，未命中才哈希和注册规则。保持类继承、`raw()`、`px()`、`ic()` 与无法静态确定时的运行时路径。

## 字段存储与冷成本

用当前 `ColorCss` 的约 200 个真实关键字构造了四种等价 JS 存储方式，在 Chrome 153 中以五个新页面取中位数。这里比较的是单条属性链的合成模型，不是完整 Vue/Svelte 更新：

| 表示方式                               | 构造 1,000 个实例 | 静态成员读 100 万次 | 动态键读 100 万次 |
| -------------------------------------- | ----------------: | ------------------: | ----------------: |
| 当前类字段                             |            4.2 ms |              5.5 ms |           43.1 ms |
| 构造函数逐项赋值                       |            4.5 ms |              5.8 ms |           43.7 ms |
| 每次构造 `Object.assign(this, values)` |           86.9 ms |              9.2 ms |           18.3 ms |
| 原型共享字段                           |            0.6 ms |              7.7 ms |           23.8 ms |

逐项赋值没有抵消它需要重复类型声明和赋值代码的维护成本；每次构造 `Object.assign` 明显更慢。原型共享有利于频繁构造主题子类和动态键读取，但回到更复杂的类型合并与首次注册机制。当前写法以静态 `s.color.red` 为主，暂不为了动态键微基准重写生成器。[V8 的属性存储说明](https://v8.dev/blog/fast-properties)与[类字段优化说明](https://v8.dev/blog/faster-class-features)提供了可能影响这些数字的机制背景，但没有给出本项目可照搬的字段数量阈值；上表只报告实测，不把差异归因于某一种 V8 内部形态。

另试过把 502 个系统 getter 改为一次 `Object.defineProperties` 批量安装。合成探针重复安装 50 个新类时，逐条 `defineProperty` 约 139.6 ms，批量约 144.2 ms，没有可用收益；保持当前简单实现。

## 组合缓存：命中更快，未命中更慢

当前规则注册器对 `parts.join('')` 的完整结果查一次 `Map`。以 `color:red;` 加 16 个反复变化的 `width` 声明比较另一种按两个原始字符串分层的 `Map`：

| Chrome 153 合成负载 | 当前完整字符串缓存 | 额外的双片段缓存 |
| ------------------- | -----------------: | ---------------: |
| 100 万次已存在组合  |           240.5 ms |         159.1 ms |
| 1 万次新组合        |            27.2 ms |          31.3 ms |

双片段缓存少做字符串拼接，却增加索引、内存和未命中工作。当前系统已经避免在命中时哈希和写 CSSOM；对有限状态，更简单的办法是预注册少数完整类，然后只按状态选类名。持续新值的场景更适合评估元素级 CSS 变量，不能盲目加一层全局缓存。只有真实负载显示大量重复的二片段调用时，才值得考虑受控的专用缓存。

## 直接字段让哪些静态优化变得容易

[AST 探针](../test/tools/static-field-probe.mjs)直接读取生成类的字符串字段和 `Css` 的属性类型映射，不实例化作者对象。它能把以下表达式枚举为完整声明，并用现有规则注册器核对类名：

```ts
css(s.display.flex, enabled ? s.color.red : s.color.blue);
// display:flex;color:red;  -> z-9zpb0c
// display:flex;color:blue; -> z-1ltp125

css(s.display.flex, ic('&:hover', s.color.blue));
// display:flex;&:hover{color:blue;} -> z-2rtwdv
```

它也能扫描 `switch` 中分别出现的 `css()` 调用，把静态分支列为候选；`css(s.width.px(width))` 因 `width` 未知，明确标成运行时回退。这只是**候选规则提取**，尚未改写组件或运行时调用。真正的 Vue/Svelte 编译优化还必须：通过类型信息确认 `s` 是哪个 `Css` 子类，尊重用户字段覆盖；保留 `if`／`switch` 的控制流和表达式副作用；给分支组合设置上限；让编译端和运行时共用同一类名算法；处理 CSS 输出、SSR、hydration、HMR 与源码位置。不能只按变量名 `s` 和字段文本猜测，也不能把未知 `raw()`、`px()` 强行静态化。

一个合理的代码边界是：框架无关的**构建期**分析器只接受已确认类型和来源的表达式并返回静态声明候选，不进入浏览器 `core` 运行时；Vue/Svelte 适配器负责在组件编译前识别并改写模板，保留源映射和运行时回退。Vite 的 [plugin transform 与 `enforce: 'pre'`](https://vite.dev/guide/api-plugin) 可以作为 Vue 一侧的接入探针；Svelte 官方编译器提供 [`parse({ modern: true })`、`preprocess` 与带源映射的 `print`](https://svelte.dev/docs/svelte/svelte-compiler)，可作为另一侧探针。这里只确认有接入口，**尚未验证这些入口与当前 Vue/Svelte 插件、Nuxt/SvelteKit 构建顺序的实际兼容性**。

即使静态分支能在构建时生成 CSS，也只有当消费端不再需要完整 `Css` 作者对象时，打包器才可能移除那约 500 KB 的运行时代码；复杂表达式仍导入并使用原运行时，不应承诺所有组件自动变小。

最有希望的下一步是**可选的静态组合优化**：仅提取已证明为固定字符串的分支，预生成完整规则与类名；遇到动态值、复杂函数或无法确认的主题覆盖时，原样保留运行时 `css()`。这样利用了直接字段的清晰结构，又不要求放弃运行时 CSS。按片段缓存与批量 getter 注册暂不进入产品实现。
