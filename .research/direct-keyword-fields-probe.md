# 关键字直接字段试验

本轮把每条属性链上的固定声明直接生成为 `readonly` 类字段。例如 `DisplayCss` 现在包含 `readonly flex = 'display:flex;'`，不再需要关键字工厂、同名类型接口、首次赋值标志和 `Object.assign`。`Css` 仍按需创建并缓存系统属性链；`css(...parts)` 仍负责连接多个声明字符串、查完整组合缓存并注册新规则。`raw()`、`px()`、主题继承与运行时回退不变。

这样做的主要价值是代码形态直观。后续可选编译器更容易从类字段读取固定声明，识别有限 `if`／`switch` 分支并预生成完整组合的类与 CSS；不能静态确定的表达式继续调用运行时 `css()`。完整组合缓存、静态片段复用、仅重算变化值以及 CSS 变量绑定也可以在旧表示上实现，**不是直接字段独有的能力**。直接字段降低的是静态分析和维护成本，不能自动提高 `css()` 的运行速度。

## 与上一提交的惰性原型版比较

下表的包体积使用同一版 esbuild 配置；“消费包”是在库构建后再次打包。Chrome 153 的微基准在七轮交错的新页面中测量，中位数只用于判断方向，不是跨设备性能承诺。

| 项目                               | 惰性原型版 | 直接字段版 |
| ---------------------------------- | ---------: | ---------: |
| 完整 `core` 入口，压缩 JS          |  589,382 B |  527,262 B |
| 完整 `core` 入口，gzip             |   84,457 B |   68,606 B |
| 消费端仅用 `ColorCss`              |    6,131 B |    6,020 B |
| 消费端使用完整 `Css`               |  577,758 B |  515,600 B |
| 浏览器执行作者脚本                 |    11.1 ms |    19.1 ms |
| 首次 `new Css()`                   |     5.2 ms |     5.8 ms |
| 动态键读取 200 万次                |    44.4 ms |    83.7 ms |
| 含动态键的缓存命中 `css()` 30 万次 |    90.0 ms |   100.4 ms |
| 再构造 `Css` 2,000 次              |     0.5 ms |     0.5 ms |
| 构造主题颜色子类 1,000 次          |     0.9 ms |     3.6 ms |

动态键探针使用 `s.color[key]`，它不是主要作者写法。另一组更接近组件代码的静态成员探针使用 `s.color.red`／`s.color.blue`：300 万次读取约 10.9／10.2 ms，30 万次缓存命中 `css()` 约 87.9／89.1 ms（前者为原型版，后者为直接字段版）。两者差异接近短时测量波动，没有证据表明直接字段会加速常见热路径。直接字段在每个主题颜色实例上重新建立约 200 个字段，因而构造主题子类的成本更高。

已构建入口的单独冷加载探针得到 `core` 约 26.2 ms；原型版以前的一次运行约 18.6 ms。这两次不是同场交错测量，不单独据此下结论，但与上表同场脚本执行结果方向一致。Vue/Svelte 各跑过一轮真实适配器正确性及更新场景；计算样式和规则数量通过，但单轮端到端耗时受浏览器负载波动明显，不能拿历史样本证明其中一版更快。

本轮先保留直接字段版，理由是源码、类型和未来静态分析更简单，完整消费包也更小；同时明确记录冷执行、动态键读取和多实例主题构造的代价。若实际应用以这些路径为热点，再评估混合生成或其他存储方式。下一步编译优化应保持完整规则中的声明顺序与原生级联，不把同属性声明拆成顺序不确定的原子类。
