# 运行时并行、SIMD 与同步快路径研究

本轮按用户决定把编译期类名提取降为可选方向，先分析现有同步 `css(...strings)`。未修改产品运行时代码；[Chrome 探针](../test/tools/runtime-hot-path.mjs)用真实规则注册器测量。浏览器为本机 Chrome 153，五个新页面取中位数。数字是不同操作的**孤立循环**，不能直接相加为一次组件更新，也不是跨设备性能承诺。

| Chrome 短声明探针                             |   中位数 |
| --------------------------------------------- | -------: |
| 已缓存的 `css('color:red;', width)` 100 万次  | 213.7 ms |
| 两片段建数组并 `join('')` 100 万次            |  79.6 ms |
| 已有字符串键的 `Map.get` 100 万次             |  14.5 ms |
| 当前 FNV-1a 哈希约 24 字符，100 万次          | 111.0 ms |
| `TextEncoder.encodeInto` 同类字符串，100 万次 | 502.7 ms |
| 1,400 条新规则，仅注册器、无 DOM              |   3.6 ms |
| 1,400 条新规则，包含逐条 CSSOM 插入           |   7.2 ms |
| 已启动 Worker 连续处理 50 条单独消息          |   6.2 ms |
| 已启动 Worker 一次处理 1,400 条批量消息       |   1.9 ms |

注册器先拼出完整声明并查缓存；**命中时不哈希、不写 CSSOM**。按本轮孤立哈希计时粗略折算，1,400 条短规则的哈希约 0.16 ms；即使这部分无成本，也只覆盖 7.2 ms 注册路径的约 2%。这是数量级上界，不是同场逐项归因。持续新值带来的规则增长与 CSSOM 写入不会因哈希更快而消失。

## 并行和 AVX 的适用边界

浏览器 Worker [不能直接操作 DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)，因此不能在 Worker 里执行本框架的 `insertRule()`。当前 `css()` 必须同步返回类名；把每次拼接或哈希发往 Worker 会引入异步消息协议。即使复用已启动的 Worker，本机单条往返平均约 0.124 ms，而主线程同类短串哈希约 0.00011 ms；批量 1,400 条的往返仍约 1.9 ms，高于主线程计算这些短串哈希的约 0.16 ms。Node 官方也建议 [worker_threads 用于足够重的 CPU 工作并复用线程池](https://nodejs.org/api/worker_threads.html)，而不是每个小任务建线程。应用服务器可以在请求级做并行渲染，但不应让 core 为单条 CSS 规则创建 Worker。

跨浏览器没有可直接指定 AVX 指令的 JavaScript API。可移植的底层接口是 WebAssembly 的 [`v128` SIMD](https://github.com/WebAssembly/spec/blob/main/proposals/simd/SIMD.md)，具体落到什么机器指令由引擎决定。当前类名使用逐个 UTF-16 code unit 的 FNV-1a，下一轮计算依赖上一轮结果；不能把原算法直接拆成独立向量 lane。Wasm 还要取得字符串数据：本轮 24 字符的 `encodeInto` **本身**比现有 JS 哈希慢约四倍；并且 [`TextEncoder` 生成 UTF-8](https://developer.mozilla.org/en-US/docs/Web/API/TextEncoder/encodeInto)，不能直接替代现有 `charCodeAt` 语义，否则含非 ASCII 值的类名会改变。

对较长字符串，结论需保留余地。约 1 KB 的合成声明上，JS 哈希 25,000 次约 96.3 ms，`encodeInto` 约 65.0 ms；此时可探索另一种块处理哈希，但仍须计入复制、Wasm 调用、类名兼容和 CSSOM。200 条约 1 KB 的新规则在本机注册约 6.6 ms，包含 CSSOM 约 6.8 ms；单靠向量化哈希不能保证整条路径明显改善。只有实际负载确实大量生成 KB 级规则时，才值得做 Wasm SIMD 或 Node 专用实现的对照探针。

## 更现实的同步优化候选

1. **一、二片段快路径。** 在同机七轮交错探针中，把 `parts.join('')` 改为单片段直接取值、双片段用 `+`，100 万次缓存命中分别约从 57.2 降到 18.8 ms、201.7 降到 182.1 ms；三个片段约 218.2／215.3 ms，新组合 1,400 次约 3.2／3.3 ms。输入按公开类型始终是字符串，组合结果与类名保持不变。真实 200 元素、30 次更新约 6,000 次调用，按微基准粗算只能节省零点几毫秒；可以作为简短、可回退的代码改动试验，不能预告明显的帧率提升。
2. **按片段分层缓存只适合高重复率。** [前一轮探针](direct-field-optimization-research.md)测得两片段百万次命中约 240.5→159.1 ms，但万次新组合约 27.2→31.3 ms，还会重复保存索引。保留当前完整字符串缓存为默认；只有真实页面显示同样片段组合反复命中且 `join` 成为热点，才考虑有界或局部的二级缓存。有限状态直接预注册类仍更简单。
3. **宿主查找不是当前优先项。** 浏览器 `css()` 经 `Document` 的 `WeakMap` 宿主，百万次命中约 208 ms；直接调用注册器约 200 ms。Node SSR 经 `AsyncLocalStorage` 的导入式 `css()` 约 299 ms，绑定宿主函数直调约 276 ms，均为百万次量级。为了这些差异改成每组件传宿主或改变已确定 API，维护成本不合算。
4. **批量插入只针对大量首次规则。** 旧探针中 1,400 条规则逐条 `insertRule()` 约 3.2 ms，一次设置预拼 CSS 约 1.6 ms；在每次新增一条时重写整张样式表则会不断重做旧规则。可在 SSR 输出或真正的批量预热中考虑一次性写入；浏览器同步 `css()` 的即时生效语义先不改。

推荐先挑**单／双片段快路径**做一个焦点补丁并测 Vue、Svelte 两轮实际更新，再决定是否保留；其余缓存、Worker 和 SIMD 暂不进入 core。持续生成新值时，用户仍可运行时写一条 `var(--x)` 规则并让框架更新元素变量，以避免无限新增类。这是运行时作者选择，不要求编译器分析分支。前期静态类名提取研究保留作可选资料，但当前不作为下一阶段前提。
