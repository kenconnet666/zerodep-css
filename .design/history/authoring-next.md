# 下一阶段作者模型：继承、bx、命名与局部配置

日期：2026-09-22。本文记录用户在阶段四审查后的确认与新增要求。以下新增 API 尚未实现；当前可用能力仍以各包 README 和 bx-compiler.md 为准。

## 用户已确认的方向

1. 运行时 css 使用原生 if、switch、循环和函数表达业务逻辑；recipes、variants 等不是既定产品目标，也不应默认排进路线。
2. 标准 CSS 基类只提供系统 CSS 能力。用户采用真实的类继承：`class AppCss extends Css`，增加自己的类型、主题色和自定义成员；主题预设通过继承扩展表达。
3. bx 的形态与能力参考 Vue SFC 样式中的 v-bind()：把 JavaScript 表达式绑定到 CSS 自定义属性，由原生响应式更新。
4. 增加候选链式入口 `s.name('xxx').config({ ... })`。name 命名整个样式构建，类名可读部分与哈希结合，方便诊断；开发阶段还希望能定位源代码。
5. config 是当前样式构建的临时配置，具体字段和作用仍待讨论，不能先实现一个任意配置袋。

这些方向优先于 phase4-audit.md 中此前对 recipes 的参考，以及把所有 bx 函数调用一律禁止的保守建议。

## Css 与用户派生类

生产化阶段已接入真实 Css 基类，使用 `css(factory, AppCss)` 选择派生类型；默认仍使用系统 Css。类型化扩展、getter、方法、super、私有字段和嵌套回调均有实际执行与类型验收。名称、完整主题作用域和自动绑定仍按后续阶段推进。

下面说明作者意图；将派生类作为 css 的第二个参数交给当前 runtime/context 即可使用：

```ts
// 已实现的类继承作者模型。
class AppCss extends Css {
  get brandColor() {
    return '#2463eb';
  }

  control(size: 'small' | 'large') {
    switch (size) {
      case 'small':
        this.padding.px(4, 8);
        break;
      case 'large':
        this.padding.px(8, 16);
        break;
    }
    this.color.raw(this.brandColor);
  }
}

class DarkCss extends AppCss {
  override get brandColor() {
    return '#8bb4ff';
  }
}
```

建议先让根级类型化值、getter 和样式方法成立，再确定如何继承属性类型以表达 `s.color.brand` 这样的扩展。不能仅放宽成字符串索引签名，也不能让类型层允许的成员在运行时被未知属性检查拒绝。

系统 CSS 元数据继续来自生成器，不手改 generated。派生类型不应通过模块级可变对象修改所有应用的默认关键字表；每个应用/请求使用的扩展类型和实例所有权应明确。普通派生成员读取仍遵循原生响应式，只有显式 bx 改走变量更新路径。

这里的“继承”首先指用户确认的类/类型继承。CSS 自定义属性的 DOM 继承可以作为主题表达手段，但不能用它替代用户要求的 `extends Css`。

## bx 对标 Vue v-bind()

已核对 [Vue SFC CSS 官方文档](https://vuejs.org/api/sfc-css-features.html#v-bind-in-css)及项目锁定的 Vue 3.5.43 compiler-sfc/runtime-dom/shared 源码。

本机小探针确认：Vue 将 `Math.max(width, 0) + "px"`、`enabled ? theme.color : "blue"` 编译为 getter，保留 ref.value 读取，CSS 中只留下变量引用。其 normalizeCssVarValue 将 null/undefined 归一为 initial，将空字符串归一为空白字符串；不只是把空值对应的属性删除，后者可能泄漏外层实例继承值。

据此，bx 的目标合同建议为：

- 作者写 `bx(expression)`；因为表达式本来就在 TS/JS 中，不需要照搬 CSS 中的引号语法，不把 `bx('theme.color')` 当成待执行的代码字符串。
- 支持组件变量、props、对象成员、算术/条件表达式，以及可在响应式 getter 中合法执行的函数调用。表达式应作为求值使用，不推荐在其中写状态或做有副作用的操作；不能把“出现 CallExpression”直接视为不合法。
- CSS 中生成稳定引用，变量当前值不进入 class 哈希。只变更绑定值时不重跑整个样式回调；普通读取和 if/switch 仍按原合同重算。
- 使用 Vue/Svelte 各自原生响应式、SSR 和生命周期。core 不依赖框架，也不新增另一套 signal/store。
- 单位方法和模板插值仍须正确组合值；不能产生 `var(--x)px`。这是本项目 typed Builder 相对 v-bind() 需要补充的部分。
- null/undefined/空字符串、非法数值和 CSS-wide 关键字应与 Vue 参照逐项比较后写入合同。上一轮 R4 的颜色差异仍是真实证据，但在新对标方向下应先作为变量语义边界处理，不能未经讨论就承诺“bx 等价于任意普通 CSS 属性赋值”或直接全禁合法关键字。

不能直接宣称作用域与 Vue 完全相同：Vue 文档描述的是组件根元素变量注入，项目 bx 首版则绑定到具体 class 使用元素。列表局部变量、复用 class、多根、嵌套实例及跨元素选择器需要保留明确的所有权。是否改变注入粒度，应以实际语义和探针决定，不盲目全提升到组件根或 :root。

### 编译与运行时的建议分工

为支持用户继承方法和原生控制流，优先探针比较以下路径：

1. 编译器负责宏身份、词法作用域、表达式 getter、稳定来源标识与元素使用点。
2. Builder 在原有同步执行过程中处理 if/switch、用户方法、单位和 CSS 声明，并收集本次真正生效的绑定描述。
3. 适配器把这些描述交给原生响应式更新与元素生命周期；绑定值不在样式计算阶段被提前读取。

这仍是待验证的内部实现方向。它的价值是避免编译器必须静态展开每个派生类方法，或把任意 JS 控制流改写为 variants。需要特别验证回调局部捕获、const 快照、反复分支切换和外部仍返回 string 的合同，不提前把内部绑定描述变成公开 API。

## s.name：整个样式构建的诊断名称

候选写法：

```ts
// 候选，name/config 尚未实现，配置字段也未定稿。
css((s) => {
  s.name('button-root').config({});
  s.display.flex;
  s.padding.px(8, 12);
});
```

建议把 name 和 config 作为该次样式构建的元信息，返回当前 Builder 以支持用户要求的链式形式。元信息不应伪装成一条 CSS 属性声明，也不能改变 css 的字符串返回值。

建议的名称合同，待实施前固定：

- name 为整个根样式命名，覆盖它包含的声明与嵌套规则；不作为 DOM id，也不创建不带哈希的全局 class。
- 输出可读前缀加内容摘要，例如 `z-button-root-<hash>`。同名不同样式得到不同摘要；同名同内容可复用。
- 不同名称但相同 CSS 内容，建议保留各自可读名称，不为了去重悄悄返回另一名称。相应的记录成本明确测量，不先做别名选择器合并。
- 建议显式名称在开发/生产环境都保留；开发专用源码信息可移除。源码文件位置不进入语义哈希，SSR/客户端及换机的身份必须一致。
- 多次 name/config、嵌套 Builder 是否能设置根元信息、名称允许字符以及名称为空时的处理必须显式规定。倾向首版在根层设置、禁止冲突重复定义，避免帮助方法意外覆盖调用者名称。

当前 namedId 同时参与类名、记录索引和 hydration 验证，不能仅修改最终返回字符串。实现必须同时覆盖序列化、缓存、manifest 及恢复校验；如 manifest 格式需要变化，明确版本边界。

### 开发阶段的源代码诊断

建议把 `src/Button.vue:42:7` 等项目相对位置保存在开发元数据、style 标签调试属性或映射表中，不把绝对磁盘路径拼进 class。编译器能可靠识别的调用点自动提供；没有编译接入的纯运行时调用不假装拥有准确源码位置，也不默认每次构建都抓取 Error.stack。

同一 class 在多个调用点复用时，应能记录多个来源。关闭开发诊断不改变 CSS 含义、类名或 SSR 身份。字段和展示形式属于诊断接口设计，尚未实现。

## s.config：候选用途与边界

用户确认的是入口形态与“本次临时配置”的意图，以下字段只是供讨论的候选，不是已批准接口：

| 候选                                 | 可能的作用                                   | 当前倾向                                                                 |
| ------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------ |
| debug                                | 为当前样式收集或显示额外诊断信息、来源信息   | 值得优先讨论；默认行为应继承宿主开发配置                                 |
| layer                                | 为当前整个样式选用一个宿主已声明的 CSS layer | 有实际用途；不得临时修改全局 layer 顺序，且必须参与输出身份和 SSR 验证   |
| important                            | 为当前整个样式设定 important 默认值          | 与已有 s.important 的表达重复，首版倾向不加                              |
| cache / validate 开关                | 临时跳过缓存或校验                           | 首版不建议开放；先由测量或调试需求证明必要性，避免掩盖错误与破坏幂等注册 |
| target / nonce / hydrate / namespace | 切换挂载位置或请求/应用身份                  | 留在 runtime/context 宿主配置，不由局部 s.config 改共享所有权            |

建议 config 只作用于本次 css 构建，继承宿主默认值，不影响随后其他 css 调用。同名字段若影响输出语义，就必须进入有效配置、摘要和 SSR 记录；纯诊断字段不进入 CSS 身份。字段应有封闭类型与验证，不使用无约束的任意对象。

现在可以先讨论 debug/layer 是否值得进入首版。没有确认实际用途前，不为了保留入口就加入空实现或忽略未知字段。

## 更新后的推进顺序

1. 继续阶段 4.1 的作用域、条件求值、源码映射修复和编译器类型检查。R4 按新 v-bind 参照改为值域/变量语义对照，不预设全部拒绝 CSS-wide 关键字。
2. 做一个 `Css -> AppCss -> DarkCss` 的继承试点，验证真实类型、成员执行、原生响应式与请求隔离；比较 bx getter + Builder 收集描述的路径。
3. 实现 name 与开发来源诊断的最小闭环，并验收命名/去重/SSR 一致性。config 待字段合同确认后一起接入。
4. 在上述边界成立后扩展原生 if/switch 和同宿主嵌套规则，覆盖用户方法调用、条件列表及绑定清理。

这些新增能力尚未进入产品代码。recipes、variants、主题预设框架不作为这些阶段的默认后续目标。
