# 下一阶段：最小可用与真实性能基线

当前 `core` 已从 `csstype` 生成 10 条属性链、680 个关键字；Vue、Svelte 已有适配原型，Nuxt 和 SvelteKit 仍是空入口。本阶段的交付边界是：**Vue 3.5 与 Svelte 5 的浏览器和标准 Node SSR 可以实际使用同一套字符串作者写法，并附有新实现的性能报告**。Nuxt 4、SvelteKit 2 的专用封装留在随后的阶段；这次不能把五包称为生产就绪。

进度：浏览器宿主与 Vue/Svelte 类型化注入、Node 请求宿主、并发 SSR 和 hydration 去重已落地并通过研究夹具；502 属性生成与正式性能报告仍在本阶段待做。

## 用户最终能写什么

以下是目标调用形态，尚不是已实现代码。项目入口只建立类型化上下文；根部创建并注入一个作者实例，后代取得同一个实例。`css()` 仍从适配包导入，`ic()` 包装原生选择器块。

```ts
// styles.ts：Vue 和 Svelte 各用自己的适配包；AppCss 继承 core 的 Css
export const { provideCss, useCss } = createCssContext<AppCss>();

// 应用根部；SSR 时每个请求各执行一次
provideCss(new AppCss());

// 后代组件
const s = useCss();
const className = css(
  s.display.flex,
  usePreset ? s.width._md : s.width.px(width),
  ic('&:hover', s.color.red),
);
```

这里 `useCss()` 只读上下文，不再创建类或空 Proxy。若缺少提供者，给出明确错误；子树可以提供另一个同类型实例覆盖上层。`css()` 将片段按顺序拼成规则、命名并缓存；相同声明组合返回相同类名，不重复写规则。属性重复、`hover` 和媒体条件由浏览器按原生 CSS 处理。响应式宽度变化在本阶段继续走**运行时重新计算类名**，CSS 变量编译优化只记录、不实现。

## 分四个可独立提交的步骤

1. **浏览器宿主与类型化注入。** `core` 保持框架无关；Vue 用带类型的 `InjectionKey`。当前 Svelte 包声明支持 `^5.0.0`，而 [`createContext<T>()` 从 5.40 才有](https://svelte.dev/docs/svelte/context)，所以先用 `Symbol` 加 `setContext/getContext` 包装出同样的项目类型，避免暗中抬高最低版本。浏览器端按 `Document` 管理样式表和去重缓存，使导入的 `css(...strings)` 能注册规则；作者实例按应用根部提供。做 Vue、Svelte 各一个最小组件示例，验证主题继承、`raw()`、`px()`、`ic()`、响应式状态改变后的类名切换，以及两个应用的作者实例不串用。浏览器规则在文档生命周期内共享，应用卸载不贸然删除其他应用可能仍在用的规则。
2. **Node SSR 宿主与恢复。** Vue 的 `renderToString`、Svelte 的 server render 都必须在各自请求的规则收集器中运行。优先探测 Node [`AsyncLocalStorage.run()`](https://nodejs.org/api/async_context.html) 是否能让独立导入的 `css()` 在异步渲染中找到正确宿主；这部分只放服务端入口，不让 `node:async_hooks` 进入浏览器包，同时把作者实例留在框架的组件上下文。并发两个内容不同的请求，断言各自 HTML 与收集到的规则不串；相同声明在不同请求中生成同一个确定类名是正确行为。客户端 hydration 识别已输出的类和规则，不重复插入。无活动宿主时明确失败，不使用可在并发请求间切换的全局可变指针。若这一内部方案无法稳定支持两种框架，先解决宿主绑定，再宣称 SSR 可用。
3. **扩成约定的 502 属性。** 在现有生成脚本上覆盖标准长属性、简写和独有 SVG 属性，保留固定关键字字符串、开放的 `raw()`、仅对长度属性提供的 `px()`，以及 `padding`、`margin`、`gap` 等少数简写各自的参数规则。保持中文短注释、来源版本、许可说明、生成结果检查和主题继承类型检查。生成文件可按首字母拆分，但手写入口不堆重复 API；检查升级后没有属性名或关键字碰撞。
4. **性能测量与针对性优化。** 使用上面两套真实适配器的生产构建重新建立基线。先测再改：若主要成本是字符串组合、哈希、缓存查找、CSSOM 插入、组件重渲染或冷启动，就只优化有证据的热点。完成后写清测试环境、样本、结果和限制；不承诺与原生 CSS 同速，也不以固定百分比作为硬门槛。

## 最小可用的验收

- Vue 与 Svelte 各有可运行的浏览器示例：`const s = useCss()` 能读到根部提供的同一 `AppCss`；系统关键字和 `_md` 有类型补全；`css(...)` 返回类名且样式真正生效。
- 重复片段只插入一次；`css(s.color.red, s.color.blue)` 保留声明顺序并显示蓝色；`ic('&:hover', ...)` 随浏览器状态生效。有限状态切换会复用规则，新值会按运行时机制生成规则。类名在浏览器与服务端一致，哈希碰撞和插入失败不会把错误规则留在缓存中。
- Node SSR 的并发请求隔离、生成规则输出和客户端 hydration 有自动化断言。缺少提供者或活动宿主时，不静默创建实例或漏掉样式。
- `pnpm check` 同时通过生成结果一致性、五包类型检查和新增类型契约；浏览器与 SSR 的集中用例在 CI 中运行。当前 `nuxt`、`sveltekit` 包通过基础类型检查，但不冒充已完成适配。

## 性能怎么公平比较

沿用研究探针的两组负载，在 **Vue 与 Svelte 分别**测，不把两者的数字混成一轮：200 个元素；16 种宽度反复切换 30 次；每次产生新宽度的场景切换 5 次；再加入不影响宽度的更新。所有方案渲染相同数量的元素并核对计算样式。正式计时串行运行，避免几个浏览器测量同时争用同一台机器；构建和静态检查可以并行。

| 基线                                                                     | 适合回答的问题                                              | 比较时的说明                                     |
| ------------------------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------ |
| 预先声明的原生 CSS 类                                                    | 有限的 16 种值切换，浏览器最低需要多少更新成本              | 它没有运行时序列化和插入成本，是下界而非等价实现 |
| 原生 CSS 变量绑定                                                        | 值持续变化而规则不增长的成本                                | 它采用变量语义；与运行时逐值生成类是不同策略     |
| 当前完整实现                                                             | 字符串访问、组合、缓存、插入与框架更新的总成本              | 同时报规则数、缓存命中和 `css()` 调用数          |
| [`@emotion/css/create-instance`](https://emotion.sh/docs/%40emotion/css) | 相同字符串片段与独立样式容器下，另一运行时 CSS 缓存器的表现 | 样式与元素一致，注明它与本框架的功能差异         |

记录冷启动/首次导入、首次注册、缓存命中、有限值更新、新值更新、无关更新、规则总数、Node SSR 单请求与并发正确性；分开报告 `css()` 本身耗时和含框架刷新、浏览器布局的端到端耗时。全量 502 属性生成后的导入与类型检查成本也要测。旧的 `.research/string-css-probe/results-*.json` 来自试验引擎，只提供场景设计，不作为本阶段正式结果。若发现新值带来持续规则增长，先量化增长与实际内存，再决定是否需要开发期诊断；本阶段不抢做 Vue `v-bind()` 式编译转换。

这四个步骤完成且验收通过，才称本阶段“最小可用”。下一阶段再处理 Nuxt 4、SvelteKit 2 的专用入口、CSP/nonce、更多浏览器与完整生产审计。
