# 后续路线

运行时优先的 P1—P6 已完成约定的生产范围；[2c51b0f 对应的九项远程 CI](https://github.com/kenconnet666/zerodep-css/actions/runs/35946894347)已通过。实现、已验证的版本与部署边界见[支持范围](support.md)和[生产记录](production.md)。以下是新阶段候选工作，不代表已承诺或已实现。

1. **补齐当前浏览器性能基线**。现有 Vue/Svelte 横向表生成于 P4c 注册优化之前，[性能文档](performance.md)也明确没有重跑。用同一锁文件、同一浏览器与交替顺序比较当前 HEAD、优化前基线和原生/Emotion 对照，同时核对样式记录数、工厂调用次数和完整输出。分开报告更新耗时、首次挂载、包体积与 CSSOM 增长；不要从 Node 注册微基准推导整页收益。
2. **按基线选一个真实热点优化**。持续新值时优先检查构建/规范化/注册与浏览器规则写入的比例；有限状态时检查缓存命中和框架更新。合并 style 节点、跨模块 `useCss` 编译识别等仍是候选，需要先证明事务回滚、规则顺序、nonce、SSR/hydration、HMR 和普通 JS 求值次数不变。编译器不能证明等价时继续运行原作者代码。
3. **扩大实际消费覆盖**。项目推荐把 `createStyles` 放在独立 `styles.ts`，当前这一路径完整运行但通常不命中同 SFC 优化。选择真实应用组件作为样本，再决定是否做跨模块静态追踪。边缘运行环境、Nuxt 3、组件 HTML 流式 SSR 及框架版本升级应各自建立独立验收，不复用 Node SSR 的成功结论。
4. **准备公开发布时再单独做发布审计**。五包目前均为 private。发布需要确定包名与版本策略、适配器 peer 范围、公开导出和真实消费示例，并重新审核依赖、许可与安全修补的传播；当前 CI 通过不等于已具备对外兼容承诺。

优先执行第 1 项。它能说明当前剩余成本在哪里，再决定第 2 项的实现，不应仅依据旧静态架构或单次 benchmark 选优化方案。普通 `if/else/switch` 与函数复用已经是运行时作者能力，recipes/variants 不是默认目标。
